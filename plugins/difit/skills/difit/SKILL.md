# Difit

## Граница применения

Запускай viewer только при явном упоминании difit или при заранее установленном требовании проекта. Обычный запрос проверить diff не означает запуск внешнего viewer-а.

## Режимы работы

- **Показать diff:** открой запрошенный target без предварительных комментариев.
- **Провести review в difit:** изучи весь запрошенный diff и нужный окружающий код, сформулируй только конкретные замечания и добавь их как inline-треды до запуска viewer-а. Если подходящий viewer уже запущен, добавь findings в него через MCP или `comment add`.
- **Обработать обратную связь:** прочитай новые события и треды, внеси запрошенные изменения, выполни относящиеся проверки и ответь в исходных тредах.
- **Только ревьюер (Reviewer mode):** если агент подключён как ревьюер для проверки diff (например, одна из нескольких моделей на ревью), его задача — изучить diff и добавить замечания через MCP `add_comment` (передавая понятное имя в `author`, например `"Reviewer (Claude)"` или `"Reviewer (GPT-4o)"`) либо CLI `difit comment add --author "..."`. Агент-ревьюер **не отвечает** в тредах, **не меняет статусы**, **не слушает события** и **не правит код**. После публикации замечаний он сразу завершает работу. Разбором правок и ответами занимается один основной агент.

При review GitHub PR или GitLab MR используй локальные refs и только read-only доступ к хостингу. Не публикуй remote-комментарии, approvals и другие изменения без отдельной просьбы пользователя.

Если findings нет, явно сообщи об этом при передаче ссылки на viewer.

## Выбор команды

Сначала проверь `command -v difit`. Если команда доступна, используй `difit`; иначе — `npx difit`. Если fallback требует недоступной сети, сообщи о блокере.

Если доступны MCP tools плагина difit, предпочитай их для чтения событий и работы с тредами.
Для запуска viewer-а из HAPI-сессии есть важное исключение: запускай `difit ... --background`
через shell текущей сессии, чтобы дочерний процесс унаследовал `HAPI_SESSION_ID`. Не используй для
такого запуска MCP `start_review`: долгоживущий MCP-сервер может не иметь идентификатора текущей
HAPI-сессии, и тогда комментарии сохранятся, но агент не проснётся. Вне HAPI предпочитай MCP и для
запуска. CLI-команды ниже также остаются fallback при отсутствии MCP.

Все команды выполняй из Git root выбранного checkout. Запуск viewer-а не разрешает сам по себе создавать или переключать ветки, выполнять fetch, merge, rebase либо менять index.

Основные targets:

- `difit .` — все текущие изменения;
- `difit . --include-untracked` — также новые файлы;
- `difit working` — только незакоммиченные tracked-изменения;
- `difit staged` — staging area;
- `difit` — HEAD;
- `difit <target> [base]` — конкретный commit или range.

Для GitLab MR сначала прочитай `source_branch`, `target_branch` и `web_url` через read-only
`glab mr view --output json`. Если checkout находится на `source_branch`, всегда открывай
интерактивный review одной канонической командой независимо от текущей чистоты working tree:

```bash
difit . <target_branch> --include-untracked --gitlab-mr <web_url> --background
```

Target `.` одновременно показывает коммиты ветки относительно target и последующие staged,
unstaged и untracked правки агента, а также включает слежение за working tree. Не запускай
интерактивный MR-review как `HEAD <target_branch>`: чистый при старте checkout может стать грязным
после принятия замечания, и пользователь не увидит исправления. Фиксированный commit-to-commit
review используй только когда пользователь явно просит неизменяемый snapshot либо checkout не
является source-веткой MR. Всегда передавай известный `web_url` явно: автоопределение служит
страховкой, а не заменяет уже полученную каноническую ссылку.

Если используется `npx difit`, замени только имя команды, сохранив остальные аргументы.

## Identity, snapshot и повторное подключение

До запуска сохрани Git root, branch, target/base, `reviewId` и фактический port. Identity live-review
включает репозиторий, ветку и base context; совпадение одного пути checkout недостаточно.

Перед новым запуском проверь, не работает ли уже viewer того же review. Переиспользуй его только
если это live-target (`.`, `working` или `staged`) с нужным checkout и base context. Если
интерактивный MR-review был ранее открыт на `HEAD` или другой фиксированный revision, до изменения
кода переподключи тот же MR канонической командой с target `.` и дальше используй фактический port
нового live-viewer-а. Благодаря переданному `web_url` сохраняются identity review и его треды.

Для повторных раундов используй `--keep-alive` или `--background`. Команды обратной связи всегда
направляй на фактический port подключённого viewer-а. Hub сохраняет последний diff как snapshot:
review остаётся доступным для чтения и комментариев, когда агент отключён или checkout переключён
на другую ветку. Такие комментарии остаются pending и доставляются после следующего запуска
viewer-а с тем же `reviewId`; не забирай их из viewer-а другой ветки.

При явном перезапуске viewer-а останови только процесс нужного review, предварительно сверив его
`reviewId`, PID и checkout. Затем из исходной HAPI-сессии и Git root этого checkout снова выполни
каноническую команду с `--background`. Не копируй полную командную строку старого процесса, не
создавай для viewer-а systemd-сервис и не передавай повторно `--comment`: сохранённые треды
загрузятся по `reviewId`, а повторный startup-import без стабильных ID создаст дубликаты в `Open`.
`--comment` допустим только при первоначальном создании новых тредов.

## Комментарии

Читать и изменять треды следует штатными CLI-командами:

- `difit comment get --port <port> --format json`;
- `difit comment add --port <port> '<json>'`;
- `difit comment reply <thread-id> --port <port>`;
- `difit comment edit <thread-id> <message-id> --port <port>`;
- `difit comment accept <thread-id> --port <port>`;
- `difit comment request-changes <thread-id> --port <port>`;
- `difit comment verify <thread-id> --port <port>`;
- `difit comment ready <thread-id> --port <port>`.

MCP-эквиваленты: `get_comments`, `add_comment`, `reply`, `edit_message` и `set_thread_status`.

Текст ответа передавай через quoted heredoc, чтобы shell не изменил Markdown:

```bash
difit comment reply <thread-id> --port <port> <<'DIFIT_REPLY'
Текст ответа.
DIFIT_REPLY
```

Статусы показывают, чей сейчас ход. После `Open` пользователь выбирает одну из двух веток:

- внешняя правка: `Open` → `Changes Requested` → `Verify Fix` → `Ready` → `Resolved`;
- правка текущим агентом: `Open` → `Agent Working` → `Ready`.

Значения статусов:

- `Open` — замечание обсуждается; агент может анализировать, отвечать и предлагать решение, но не
  имеет права менять код;
- `Agent Working` (`accepted` в API и событии, `Assign Agent` в UI) — пользователь поручил
  текущему агенту внести правки;
- `Changes Requested` — пользователь передал замечание внешнему автору и ждёт его исправления;
- `Verify Fix` (`to_verify` в API) — пользователь просит текущего агента проверить уже появившуюся
  внешнюю правку;
- `Ready` — агент закончил собственную реализацию или успешно проверил внешнюю правку, ответил в
  треде и выполнил относящиеся проверки;
- `Resolved` — пользователь проверил результат и окончательно закрыл тред.

Только пользователь выбирает `Assign Agent`, `Request Changes`, `Verify Fix` и `Resolve`. Не
редактируй код по треду в `Open` или `Changes Requested`, даже если решение кажется очевидным:
дождись события `accepted`. Получив его, реализуй согласованное в треде решение в текущем working
tree независимо от автора PR. Статус `Changes Requested` означает, что исправление делает внешний
автор; не вмешивайся, пока пользователь не переведёт тред в `Verify Fix`.

Агент может поставить `Ready` только после фактического изменения кода с проверками либо после
успешной обработки `Verify Fix`. Перед `Ready` для изменённого кода проверь, что подключённый review
использует live-target и его актуальный diff содержит изменённые файлы; одной проверки локального
`git diff` недостаточно. Если проверка из `Verify Fix` не прошла, ответь и верни тред в `Open`. Для
обычного вопроса или обсуждения ответь, но оставь текущий статус без изменений. Получение или
подтверждение событий через `get_events` / `ack_events` само по себе никогда не является причиной
менять статус.

## HAPI wake-up inbox

Viewer, запущенный командой из shell текущей HAPI-сессии, наследует её идентификатор и будит эту же сессию при новом или изменённом сообщении пользователя, а также после `Assign Agent` или `Verify Fix`. Для такого viewer-а не запускай watcher и не удерживай model turn.

После wake-сообщения получи durable batch:

```bash
difit comment events --port <port>
```

При доступном MCP вместо команды вызови `get_events` с тем же port.

Каждое событие несёт `type` и `threadStatus` треда на момент постановки в очередь:

- `accepted` — тред назначен тебе через `Assign Agent`: реализуй договорённость с проверками и
  поставь `Ready`;
- `userMessage` при `threadStatus` `accepted` или `ready` — уточнение к уже порученной работе:
  выполни и, если менял код, верни `Ready`;
- `userMessage` при `threadStatus` `open` — вопрос или замечание: ответь, код не меняй;
- `toVerify` — просьба проверить внешнюю правку: прогони проверки, поставь `Ready` либо верни
  `Open`.

Статус в событии мог устареть к моменту обработки; перед действием сверься с `get_comments`.

Обработай все события из ответа. Только после полной обработки подтверди точный `throughSeq`:

```bash
difit comment ack <throughSeq> --port <port>
```

При доступном MCP вызови `ack_events` с port и точным `throughSeq`.

Не подтверждай batch заранее. Несколько сообщений объединяются за одним outstanding wake-up и не прерывают текущий turn. События новее подтверждаемого `throughSeq` остаются pending и вызывают следующий wake. Неподтверждённые события сохраняются и могут быть доставлены повторно после restart.

Используй этот режим только если viewer запущен из текущей HAPI-сессии или его привязка к ней достоверно известна.

## Watcher fallback

Если HAPI-привязки нет, используй один встроенный durable watcher:

```bash
difit comment watch --port <port> --cursor-file <cursor-file>
```

Отдельный cursor нужен для каждого review. Не добавляй поверх команды polling, второй restart-loop или дополнительный watcher. Пока идёт интерактивный review, продолжай читать вывод watcher-а; при паузе останови только watcher, оставив keep-alive viewer доступным для продолжения.

## Startup comments

Контекст или findings можно добавить при запуске несколькими аргументами `--comment`:

```bash
difit . --include-untracked \
  --comment '{"type":"thread","filePath":"src/example.ts","position":{"side":"new","line":12},"body":"Комментарий"}'
```

Используй `side: "new"` для строк target и `side: "old"` для удалённых строк. Для диапазона передай `line: {"start": 12, "end": 16}`.

Inline-комментарий пиши на языке пользователя и начинай сразу с дефекта или вопроса. Покажи достижимый сценарий и конкретное последствие; не называй общий риск без объяснения пути до ошибки. Утверждай, что проверил поведение, только если действительно воспроизвёл его. Добавляй команду, вывод или готовый фрагмент исправления лишь когда они помогают автору проверить замечание. Не копируй в комментарии и аргументы команд credential-like данные из diff.

## Завершение

Если процесс завершился и вернул комментарии, продолжи работу над ними. Завершение без комментариев
означает, что замечаний не было; повторно запускать viewer только ради проверки не нужно.
Жизненным циклом внутренних viewer-процессов пользователю управлять не требуется. Удаление review
через dashboard необратимо удаляет его snapshot, комментарии и pending events; никогда не удаляй
review за пользователя без явной просьбы.
